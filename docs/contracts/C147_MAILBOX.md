## Schema and ownership
Character-owned player_mail Storage objects use deterministic source-derived IDs. Immutable delivery ledger player_mail_deliveries prevents re-delivery after purge. Fields: id, category(system/event/battle_report), source_type, source_id, title, sender_name, body, attachments[{type(resource/item/hero/exp),id,amount}], created_at_ms, expires_at_ms(null=infinite), purge_at_ms(null), read_at_ms, claimed_at_ms, deleted_at_ms, version. Character keys include server_id and generation via characterRuntime; legacy account scope remains supported. Assets are presentation-only through AtlasRegistry/UiSkin.

## RPC request/response
All player RPCs authenticated, account/session guarded, version gated and server admitted. mail_summary {}; mail_list {filter:all/unread/read/reward/expiring/system/battle_report,cursor?,limit?}; mail_open {id}; mail_claim {id}; mail_claim_all {cursor?}; mail_delete {id}; mail_delete_read {cursor?}. Response {success,code?,message?,server_time_ms,summary:{unread_count,claimable_count},mails?,mail?,next_cursor?,has_more?,results?,profile?,inventory?,heroes?}. Keyset pagination newest-first; bulk operations use bounded stable ID cursor across the entire mailbox, return per-mail result and next_cursor. Client handles every batch. No client-authoritative rewards or local fallback.

## Rules
Read changes only after successful open. Expired at server_now >= expires_at: claim rejected. Defaults warning=24h, retention=7 days, overridden by validated published system.mailbox settings. Infinite mail has no purge deadline. Worker physically deletes expired/soft-deleted mail with version preconditions; immutable delivery ledger survives. Manual delete only when there are no attachments or all attachments are claimed, even after expiry; delete-read additionally requires read. Atomic Storage CAS writes mail+profile+inventory+heroes, including progression EXP and unlock rules. All-or-none per mail, bounded bulk independent results; retry of successful claim is idempotent. Item and hero definitions resolve server-side. Delivery once per source/character even after deletion. Push code 147 is a hint, never a reward command. UI synchronizes login/reconnect/resume/open, fences old account/context/epoch replies and coalesces pushes.

## Producers and operator interface
mail_admin_send {target_user_id,server_id?,generation?,source_id,title,body,category?,attachments?,expires_at_ms?}; mail_admin_campaign {campaign_id,server_id?,generation?,title,body,attachments?,expires_at_ms?}; mail_tick {} is HTTP-key-only or configured admin, no player access. Campaign snapshots recipient population by creation cutoff, scans ready characters/users in bounded batches and retains durable progress. Repeated source/campaign ID does not mutate delivered rewards. Purchases deliver currency, items and heroes through infinite mail; verified VIP credit and entitlement rights apply immediately in the same purchase batch. Weekly awards are materialized lazily on mailbox recovery and by scheduler; original claim markers and mailbox claims commit together to prevent duplicate legacy claims.

## Arc-open notifications (1.1.1, user correction)
Ordinary stage victory/defeat never creates mail. A new source arc_opened:<arc_id> is delivered only when a persisted profile gains an arc not in its prior unlocked_arcs (excluding training arc_0). Notice is a rewardless system message, created atomically with the profile update and immutable delivery marker. Repeat progress/arc replay cannot send it again. Hook covers stage settlement, tribulation, mail EXP claims and sweep worker profile writes. Battle-report category remains supported for explicitly sent reports, not automatic per-stage mail.
